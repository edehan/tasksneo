# 数据政策

本文档定义数据所有权、删除行为与可回收策略。

## 数据所有权层级

```
用户
└── 拥有：个人空间（班级）
    └── 拥有：任务（在个人空间中创建的）
        └── 拥有：任务附件

班级（由某用户拥有）
└── 拥有：任务
    └── 拥有：任务附件（任务正文中的内联媒体）

任务
└── 包含：提交（每个成员一条）
    └── 包含：提交附件

用户
└── 拥有：提交（跨所有班级）
└── 拥有：用户头像附件
```

关键结论：`submissions` 只与 `tasks` 关联，不直接归属于 `classes`。

---

## 附件总规则

1. 附件通过四选一归属：`submissionId` 大于 `taskId` 大于 `classId` 大于 `avatarUserId`。
2. 归属对象编辑时，可删除其名下任意附件。
3. 归属对象删除时，其名下附件全部删除（数据库记录 + MinIO 对象）。
4. 任务是特殊对象：
   - 软删除任务时，也会删除该任务所有附件。
   - 硬删除任务时，同样删除该任务所有附件。

---

## 删除规则

### 删除提交

所有权上，提交属于创建它的用户；能删除提交的应该且只应该是该用户（即便 v1 暂未暴露自助删除入口）。

执行步骤：
1. 删除该提交的所有附件（DB + MinIO）。
2. 硬删除 `submissions` 记录。
3. 检查该提交关联任务是否满足“孤立可回收”条件：
   - `task.classId IS NULL`（已不归属任何班级）
   - 该任务 `submissions` 数量为 0
   - 满足则对任务执行硬删除。

---

### 删除任务

由班级 OWNER 或 ADMIN 执行。

**情况 A：任务无提交（0 条）**
- 硬删除任务。
- 同步删除任务附件（DB + MinIO）。
- `task_user_state`、`notification_jobs` 等关联记录由关系约束/应用层同步清理。

**情况 B：任务有提交（>=1 条）**
- 仅软删除任务，不删除提交。
- 软删操作：
  1. 写入软删标记（`deletedAt`）。
  2. 清空正文，保留任务的元数据（如标题、起止日期等）。
  3. 删除任务附件（DB + MinIO）。
- 查询待办任务时必须排除软删任务（例如 `deletedAt IS NULL`）。

---

### 删除班级

由班级 OWNER 执行。

班级删除过程：
1. 遍历该班级下所有任务。
2. 对每个任务执行任务删除规则：
   - 无提交 -> 硬删除
   - 有提交 -> 软删除，并将任务从班级解绑（`task.classId = NULL`）
3. 删除班级记录及成员关系。

结果约束：
- **绝不删除 submission**。
- 可能出现“只有元数据且不再归属班级”的任务（临时僵尸元数据），这是预期设计。
- 这些任务不是“真正僵尸数据”，因为后续在提交被删空时可以被系统自动硬删除回收。

---

### 删除用户

#### 前置条件（普通用户删除）

- 若用户是任意共享班级 OWNER，拒绝删除，要求先转让或解散这些班级。
- /admin平面管理用户不提供删除用户的选项。管理员有必要删除的时候应该通过重置密码-手工登陆-从用户中心中删除账户的方式进行删除。

#### 删除序列

1. 删除该用户的所有提交（按“删除提交”规则执行，含孤立任务回收检查）。
2. 删除该用户的私有班级：
   - 由于该用户提交已先删除，私有班级内任务应满足 0 提交，均可硬删除。
3. 删除用户记录本身，连带清理：
   - 凭据、通知偏好、成员关系等
   - 用户头像附件（及对象存储）
   - 各类指向该用户的可空引用按约定置空

---

## 僵尸数据定义

- 允许存在“暂时不归属班级但仍被 submission 引用”的软删任务元数据。
- 不允许存在“系统永远无法访问和回收”的真正僵尸数据。
- 回收机制：当最后一个 submission 被删除，且任务 `classId = NULL` 时，任务应被硬删除。
